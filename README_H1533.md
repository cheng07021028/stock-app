# V191-H153.3｜中央自動排程卡住與永久同步失敗隔離

## 基準及適用情境

接續 H153.2 累積差異包（可覆蓋原 H146 完整程式），只修正實際第17頁中央排程卡住、10頁隔日命中網路拉取無上限、同輪重複永久同步、失敗原因難辨識等問題；H126 正式交易資格與選股排名不變。

## 經實檔定位的根因

1. `pages/10_推薦清單.py::_update_night_hit_tracking_v101` 原排程預設最多 300 筆，每筆可呼叫三種行情來源。
2. `godpick_history_sources.py::fetch_twse_tpex_daily_range` 在 Yahoo/Stooq 都失敗後，最多逐日遍歷120天，且每一天查一至兩個官方端點；`timeout=7` 只限制**單一 HTTP 請求**，無法限制整批或120天查詢，因此出現長時間等待。
3. `godpick_auto_scheduler.py::_checkpoint_runtime` 原先在每個 job 前後各同步保存 status 和 history，遠端多次寫入在失敗時反覆等待；預設失敗還會立即重跑2次。
4. `godpick_auto_update_tasks.py` 的第6～10工作都可能獨立重新嘗試推薦紀錄與清單的 GitHub / Firestore 永久同步，累積等待又相互重複。

## 修正

- **排程隔日命中**：每輪預設至多6筆，最多12筆（兼容舊設定300）；軟時間預算預設28秒，個股行情查詢每一 HTTP 請求4秒，已完成列留下追蹤更新時間，下一輪優先續跑未處理列，再按最舊更新日期輪替。超過軟預算不再啟動下一筆，未處理保留、摘要可稽核。
- **自動行情備援**：排程停用逐日×120天官方請求的慢速備援（Yahoo/Stooq快速來源仍在），資料不足明確標示。第10頁原**手動**追蹤及其他 API 呼叫沿用全部行情來源，未刪功能。
- **排程checkpoint**：每項工作前後立即原子儲存本機 status/history；整輪結束或人工暫停時才同步遠端永久確認。中途 checkpoint **不冒稱遠端已保存**，遠端保存失敗仍回報失敗。執行排程之前請確認 GitHub/Firestore 的遠端權限，避免 Streamlit Cloud 重啟後只有本機 checkpoint。
- **單輪遠端故障隔離**：6～10工作如明確出現永久同步失敗，後續相同遠端權威工作本輪標記 BLOCKED/待下次重試，不列成功；17 永久化恢復工作保留。工作層級即時重試預設0次，舊自訂仍最多1次。
- **錯誤定位**：從同步回報提取安全的 HTTP 401/403/409/422/429 或逾時/Token缺漏摘要。保留詳細 message 供 17 頁查核；不輸出憑證。
- **保護**：推薦歷史、最新推薦、設定、Secrets、H126 及 12 張 Excel 工作表完全不覆蓋、不刪除。

## 部署

在實際 GitHub `main` 的最新程式上先比對衝突與更版；只有確認相同或適用的來源再合併本 ZIP。不可只部署舊 H153.2 檔案回退最新線上功能。測試 `python tools/h1533_verify_deploy.py --root .`；第17頁執行人工測試，確認第10項在合理時間內結束、顯示待續筆數，遠端恢復後回報永久確認。若遠端仍失敗，查 GitHub runtime-data 分支 Contents write 權限／分支保護／Firestore 與 Token。

## 已知限制

軟預算不是強制中止已開始的 requests；單筆 Yahoo/Stooq 仍可能各自重試，排程使用的小批次與禁用日官方逐日備援大幅降低風險。同步成功仍取決於真實網路和遠端權限，本機模擬無法保證雲端即時永久保存。不得將本次代碼修復當成正式雲端服務驗收。
